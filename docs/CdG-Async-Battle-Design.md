## 1. 目的と機能範囲

- 他のプレイを再現したリプレイと、自分のプレイで非同期の2人対戦ができる。
- 推薦ロジックで独立してプレイする「あひる先生」と対戦できる。
- 一人用・対戦を含む全モードのプレイを、圧縮・難読化したテキストとして受け取れる。
- 対戦中に双方の進行・ステータス・暫定スコア・デッキを比較し、結果画面で勝敗と2人分の評価を確認できる。
- プレイ履歴から過去の結果を確認し、お気に入りとして保護したり、完全なリプレイデータをテキスト出力したりできる。

リアルタイム通信対戦、サーバーでのマッチング、リプレイ共有サイトは初回要望に含まれていない。

## 3. 相談で決定したこと

### D01：勝敗と同点時の判定順

最終スコアを比較し、同点なら次の優先順で比較する。先に差がついた項目で勝敗を確定する。

1. 入退差数が多い。
2. 退塾数が少ない。
3. 体験数が多い。
4. 満足が高い。
5. 経理が高い。

全項目が同じなら引き分けとする。主判定の最終スコアは画面表示値 `displayScore` を使い、FRESHの精度スコアやイベント加点を含める。基準別得点 `points` だけで比較しない。

### D02：退塾予備軍の基準値X

1ターン目は1。その後、毎ターン2ずつ増加し、8ターン目は15とする。

| ターン | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| X | 1 | 3 | 5 | 7 | 9 | 11 | 13 | 15 |

ターン番号を `t = 1..8` とすると、`X(t) = 2t - 1`。初回要望の「開始時1、1ターン目を含む開始時に+2」は、この数列を正として具体化する。

退塾予備軍数は、現行の退塾計算の15をXへ置き換え、次の式とする。

```text
退塾予備軍数 = max(X - 満足, 0) + max(X - 経理, 0)
```

暫定入退差も `入塾 - 退塾予備軍数` とし、既存の基準別得点・精度加算へ渡す。これにより退塾の基準だけを差し替える。最終結果には通常の基準15を使い、8ターン目終了時は暫定値と最終値が一致する。演出中は画面に反映済みの数値から暫定スコアを更新し、相手の未公開の解決結果を先に反映しない。同値の背景は基準色とする。

### D03：特殊条件のリプレイとの対戦とイベント選択

自分側は通常ルールを基本とし、イベント・計算機などの特殊条件で記録されたリプレイとも対戦できる。

- 全モードの完走済みで記録が完全なプレイを、リプレイ出力・対戦利用の対象とする。途中終了・記録不足はD06に従う。
- 相手リプレイは記録元のモード・効果・選択を再現する。
- 自分側へ計算機モードの手入力や特殊初期条件を自動で引き継がない。
- 現在がイベント開催期間中なら、特殊モードのリプレイとの対戦で、自分側へイベントを適用するかロビーで選べる。
- 開催期間外に自分側へイベントを新規適用する要件はない。相手リプレイの記録元のイベントは再現する。
- FRESH / PROはリプレイに合わせる。

双方に適用されるモードで、それぞれ本来のスコアを計算する。イベント由来の相手には上限超過加点を含む。ロビーでは条件の違いを示すが、相手の最終点・最終デッキは表示しない。自分側へ適用するのは対戦時に開催中のイベントとし、相手の記録元のイベントへ自動的に合わせない。終了済みイベントを含む相手の再現には、元プレイで確定した効果結果を使う。現在のイベント期間や抽選で相手の記録を上書きしない。

### D04：CPUの強さ・採用方針・ロビー

- CPUの強さは1通り。
- 取得・配置・削除・リフレッシュは、開発済みロジックのうち「リセマラなし・8点以下防止・平均12点狙い」の方略に従う。
- CPU対戦のロビーでは、FRESH / PROだけを選ぶ。強さの選択肢は設けない。

この指示を公開取得アシストの軽量な推薦式だけへ置き換えない。「8点以下防止・平均12点狙い」は方略を指定する表現として記録し、全対戦で8点以下にならない保証や、FRESHで平均12点を出す要件とは扱わない。FRESHの通常スコア上限は10点であるため、PRO向け方略に対応するFRESH側のロジックを区別する。

指定に対応するPRO方略は、リセマラなしの固定自動方略V1。0059の `docs/CdG-PRO-One-Shot-Guide.md` と `solver/research-results/ahiru-advice-20261103/goal-3percent-assessment.json` で、先頭1,000開始を全採用して平均12.026点、8点以下26件の2.6%と記録されている。公開アシストと同一ではない。

| 項目 | 特定した採用元 |
|---|---|
| 固定ソース | `04d200e157156837a7bb326920ecd641707a90c6` |
| 設定 | `solver/research-scenarios/ahiru-pro-stability-configs.json` の `baseline` |
| 取得・配置・削除・リフレッシュ | `learned` / `engine` / `aggressive` / `learned` |
| 先読み | 8個の仮想将来、2ターン先読み |
| 方略11ファイルのSHA-256 | `8196136e4d19da110d40ee9187a98e97dfe7b64adacf53a2a51c25bd1904ad59` |
| 固定平均モデル | `solver/models/pro-public-value-v1.json` |
| モデルのSHA-256 | `c07e7fe747c66aeebb345a2f3100ae6b6fc4609605ea58680230e6ac94be9bba` |

移植時は `solver/browser/pro-strategy-research.js` の `createResearchPolicy` を起点とし、`acquisition` / `placements` / `deletions` / `learnedPolicy.refresh` と、実行側のリフレッシュ条件を一緒に引き継ぐ。新しい研究方略へ無断で差し替えない。

FRESHは、既存の取得 `reach`、配置・削除 `fresh_stable` を採用する。0059の `docs/CdG-FRESH-Assist-Analysis.md` に、別の1,000開始でS以上87.6%、中央値8.9点の記録がある。

### D05：相手情報の公開範囲

- 対戦前のロビーでは、相手の最終点・最終デッキを公開しない。
- 対戦中は、相手の手札・未解決の配置・未来の結果を隠す。
- 相手のカード一覧では、既存のカード配置画面と同様に、手札と山札を区別せず「山札」としてまとめて表示する。
- C08の相手デッキ内訳も、その時点の所有構成を対象とし、最終構成を先に表示しない。
- カード効果解決演出では、C09に従って自分の演出後に相手のカード・結果を公開する。

相手の手札の所属を推測できる区分や、未解決の配置を一覧・詳細・助言文から先に見せないよう、表示用の状態を分ける。

### D06：リプレイ出力できるプレイ

完走し、再現に必要な記録が完全なプレイだけ出力できる。途中終了・記録不足のプレイは出力を認めない。この制限は結果画面と履歴詳細の両方に適用する。

既存履歴には得点・最終デッキなどの要約しかないため、完全なリプレイは復元できない。旧履歴の閲覧は維持し、存在しない操作・状態を推定してリプレイ出力しない。

### D07：同一シード時のハイスコア

「リプレイデータと同一シード」で対戦するときは、ハイスコアを記録しない。この条件でも、D08の履歴保存・GAS送信は行う。

別シードでの対戦結果のハイスコアは、1人プレイと同じ対象条件に従う。CPU対戦のロビーはD04に従ってFRESH / PROだけを選ぶため、C02のシード選択はリプレイ対戦のロビーに適用する。

### D08：対戦結果の履歴・GAS送信

対戦結果の履歴保存・GAS送信は1人プレイと同じように受け付ける。同一シードを理由に履歴保存・送信まで除外しない。履歴50件・未送信の直近5ゲームという既存の上限を引き継ぎ、お気に入りによる保護は履歴に適用する。

端末内の履歴には、自分の結果・相手の結果・勝敗を保存する。GAS送信は自分の結果だけを対象とする。リプレイ出力も自分1人のプレイを対象とし、相手のリプレイを入れ子に複製しない。再送・二重登録防止・通信中の再プレイという既存の挙動は維持する。

### D09：全モード共有の中断データ

中断データは、現在と同様に全モード横断で1件だけ保持する。別のモードへ移動するには、初めからやり直す必要がある。対戦用の別セーブ枠は追加しない。

対戦中断では、自分・相手の進行状態と演出位置をまとめて同じ1件へ保存する。保存した対戦を再開する場合は、開始時の条件を保持する。

### D10：プレイ履歴・お気に入り・リプレイ出力

| ID | 決定した要件 |
|---|---|
| H01 | 結果発表画面で、そのプレイを「お気に入りに追加」できる |
| H02 | 設定画面の「プレイ履歴」から履歴を振り返り、お気に入りへの追加・お気に入りからの削除ができる |
| H03 | 特定の履歴を開くと、プレイ内容を確認できる |
| H04 | 履歴詳細に、リプレイデータをテキストとしてクリップボードへ出力するボタンを設ける。D06を満たす履歴だけ出力できる |
| H05 | お気に入りは最大49件 |
| H06 | 履歴全体の保持上限は50件。追加で51件以上になったら、お気に入り以外で最も古い履歴を削除する。お気に入りは自動削除の対象から除く |
| H07 | タイトル画面に「プレイ履歴」ボタンを置く |

お気に入りは保持する50件の内数とする。50件の通常履歴に別枠で49件を追加する方式にはしない。「お気に入りからの削除」は保護の解除を指し、その場で履歴そのものを消す操作とは分ける。

49件がお気に入りの場合も、新しいプレイを1件保持できる。次のプレイが完了すると、既存の非お気に入り1件が最古なら、その1件を削除して新しい結果を残す。お気に入り操作で完了順を変えず、50件目のお気に入り追加は既存の49件を維持したまま受け付けない。

お気に入りにした履歴から後日リプレイ出力できるよう、要約だけでなく完全なリプレイを履歴の存続期間中保持する。圧縮済みリプレイの保存方法・保存容量への対応は実装時に検討する。保存失敗時に、保護済みのお気に入りを黙って削除しない。

お気に入り保護後の一覧には古いプレイが残るため、「直近50件」という説明を、実際の保持規則が伝わる表記へ見直す。タイトルには既に「📚 履歴」ボタンがあるため、新しいボタンを重複追加せず、「プレイ履歴」という名称と同じ閲覧画面への導線を整える。

### D11：リプレイ対戦のアシスト

リプレイとの対戦では、取得アシストとあひる先生の助言を通常の設定どおり利用できる。CPU対戦だけはA02に従って強制無効とする。

### D12：0062公開後の表示・セリフ改善

2026-11-08の追加指示に従い、C03〜C05とCPUの文面を次のように更新する。

- PROの対戦準備中は「あひる先生が教材研究中…」と表示する。ターン単位の進捗表示は維持する。
- CPUの研修セリフは、取得前のCPUの状態と当ターンの取得予定カードを、1人用と同じ助言ロジックで評価して選ぶ。取得予定以外の候補への変更やリフレッシュは提案しない。「〜選ぶね」「〜手に入れるね」など、CPU自身の行動として話す。
- セリフは同じターン内で固定する。カード名・未解決配置・実際の将来結果は表示せず、取得する効果の方向だけを伝える。プレイヤー側の状態や選択を評価へ渡さない。

- カード効果解決演出中の相手欄は、項目名・数値・そのカードによる増減値を表示し、ランクのアルファベットは省く。増加は`+`付きの緑文字、減少は`-`付きの赤文字とし、変化0は増減表示を省略する。演出以外の相手欄は従来どおりランクも表示する。

### D14：0063公開後の会議セリフ・スコア・結果画面の改善

2026-11-08の修正相談に従い、次の変更を作業枝で実装する。0063の公開済み資材は更新せず、新しい公開番号も付けない。

- CPUの会議セリフは、実際に削除する札の種類と、会議開始時点の所有札・ステータスから選ぶ。既存の公開情報による投影で、削除後も目標を満たすと見込む項目があれば「経理は足りそう。庶務を1枚減らすね」のように説明する。そうでなければ、削除により伸ばしたい項目や手札の回転を伝える。削除しない場合は札を残す方針を伝える。
- 説明用の投影はCPUの方略を変更しない。将来の取得・未解決配置・最終結果・削除後の実状態を読まず、プレイヤーの状態や乱数も使わない。セリフは同一ターン・同一フェーズ内で固定し、25文字以内とする。
- ヘッダーのスコアは`👤 3 / 4 🐤`の形式にし、高い側の数値だけを太字にする。同点は両方とも通常の太さとする。リプレイ相手のアイコンは`🎞️`を使う。月・フェーズ・おすすめカテゴリと同じ行の右側へ置き、追従ヘッダーでも同じ配置にする。スクリーンリーダーには暫定・最終の別、両者の名前と数値を伝える。
- 対戦結果では勝敗を先頭に大きく表示し、2人のスコア・ランクを横並びのカードへまとめる。4ステータス・退塾・入退差と各獲得点は共通の比較表で確認できる。FRESHのS+加点、PROの上限超過加点も表示する。

### D16：リプレイの貼り付け対策とコードの短縮

2026-11-09、FRESHの通常プレイのリプレイを対戦ロビーへ貼ると、`CDGR1:`が小文字になり読めないという報告を受けた。添付は大文字の`CDGR1:`で正常に読め、先頭だけ小文字へ変えると0064の厳密な先頭判定で拒否された。アプリ内に小文字へ変換する処理はない。

`CDGR1:`はURLのスキームとして解釈でき、URLへ変換すると先頭が小文字になる。[WebKitの報告](https://bugs.webkit.org/show_bug.cgi?id=261936)と[修正PR](https://github.com/WebKit/WebKit/pull/18902)にも、文字列にURL表現が追加される貼り付け経路が記録されている。メモ帳では大文字、ブラウザでは先頭だけ小文字になるという症状と一致する。ただし、報告端末でのクリップボードの型と変換経路は実機では未確認であり、特定のOS版の不具合と断定しない。

- 旧形式の先頭は大小文字を問わず読む。本文のbase64urlは大小文字を維持し、本文全体を補正しない。
- 貼り付け時には`text/plain`を使う。自動修正・自動大文字化・自動補完を無効にする。
- FRESH / PROの対戦再生用に、`CDGR1.`で始まる短縮形式を出力する。コロンを使わず、URLと誤認される条件を避ける。旧`CDGR1:`も引き続き読める。
- 短縮形式では、使うカードの定義と個体の差分、カードIDの数値参照、重複する境界状態の共有、固定順の配列を使う。gzipとbase64urlは維持する。
- 初期状態、各ターンの公開状態と所有カード、カード配置と解決順、カード・塾アイテムの効果前後、削除、シード・モード・元ビルド、最終評価・最終デッキを保つ。対戦で参照しない分析ログ・乱数の途中状態・重複したチェックポイント・未取得カードの一覧は出力しない。ゲーム中の完全な記録とCPU方略は変更しない。
- 短縮形式の復元先は対戦用の時系列データとし、完全な内部診断記録の復元は用途に含めない。対応していない難易度や対戦用の構造を持たない記録は旧形式の出力を維持する。
- 既存履歴は詳細を開いたときに短縮版を準備する。変換完了までは元コードを保持し、変換失敗時も元コードをコピーできる。お気に入り・評価・最終デッキ・送信情報は変えない。別のウインドウでコードが更新された場合は古い変換結果で上書きしない。
- 変換はコピーボタンを押す前に行い、コピー操作中に非同期の再圧縮を挟まない。中断や再読み込みからも元コードでやり直せる。

改竄防止の署名や認証は追加しない。壊れた構造・参照切れ・過大な展開は拒否し、参照から復元した後も8MiBの上限を守る。今後、ゲームの互換性を失う更新では様式の変更を許容する。

新形式には今回以降の読込み処理が必要であり、この改修より前の読込み処理は新形式を認識しない。旧形式から新形式への読込み互換を維持し、ゲームデータの互換判定は上8桁を使い続ける。

## 5. 実装方式

### 5.1 リプレイとシード

- 相手リプレイは記録元のシード・モード・確定選択を固定して再現する。
- 同シードがオフなら自分側だけ新しいシードで開始し、オンなら相手の元シードを自分側に使う。
- 同シードは同じ乱数条件を意味する。取得・削除・リフレッシュやモードが異なる場合、候補や手札がすべて同一になる保証はしない。選択が異なっても候補・手札を一致させる要件なら、別途抽選方式を設計する。
- 対戦で出力するリプレイは、D08に従って自分1人のプレイだけを再現できる形式とする。過去の対戦相手のリプレイを入れ子に複製しない。
- 完全再現用の初期条件と、ターン／フェーズごとの確定状態・演出結果を保存する。分析ログの3,000件上限から独立させ、特殊モードや下4桁違いでも確定結果を再現できるようにする。
- テキストには形式識別子・元ビルド・難易度・モード・シードと再生内容を格納する。D16以降の対戦用データは`CDGR1.`に続くgzip圧縮済みデータのbase64url表現とし、旧`CDGR1:`の読み込みも維持する。
- 内部の読込み処理は、文字列形式・展開後サイズ・データ構造・ビルド互換性を検証する。展開後の上限は8MiBとし、欠けたターン・演出結果・会議結果や破損データを拒否する。後続の対戦ロビーでは、読込み失敗の理由を画面表示する。

短縮形式の圧縮前データは、次の順序のJSON配列である。対戦で必要な情報を先に整理する方が、元の記録をそのままバイナリ化する試作よりも短くなったため、この方式を採用した。配列の順序を変更するときは形式番号を変更する。

| 位置 | 内容 |
|---|---|
| 0 | 元ビルド・難易度・モード・シードなどのメタデータ |
| 1 | 使用するカード定義と塾アイテム定義 |
| 2 | カード個体IDの一覧 |
| 3 | 各個体の定義番号、定義から異なる項目、削除する項目 |
| 4 | 重複をまとめた境界状態の一覧 |
| 5 | 初期状態の番号 |
| 6 | 各ターンの配置前後・カード配置・効果・会議前後・削除情報 |
| 7 | 最終評価、最終デッキ、最終状態の番号 |

境界状態は、ターン・フェーズ・4ステータス・山札・手札・配置・一時領域・トークン・イベントの有効性を固定順に持つ。ステータスの順は体験・入塾・満足・経理とする。カード参照は位置2の番号、状態参照は位置4の番号を使う。復元したカードの属性・カード順・所有区分と、効果前後の値を元記録と比較して検証する。

### 5.2 独立した二者の進行

- 自分側と相手側で、ゲーム状態・カード管理・乱数・研修プール・トークン・イベント状態を分ける。
- 対戦を管理する層がターンの対応と演出順を制御する。CPUとリプレイの相手を共通の進行入口で扱う。
- CPUは自分自身の状態から判断し、プレイヤーの手札・選択・進行に応じて判断を変えない。
- 相手の未来の手札・取得・最終デッキ・最終点を、現在の比較表示へ先に反映しない。D05に従って公開する。
- 双方の状態・相手種別・元リプレイ・乱数・演出完了位置を1件の中断データとして保存する。既存の一人用保存と判別する。
- 通常／スキップ／中断再開で、両者の最終状態・勝敗・再出力データが一致するようにする。

実装では、CPUの1プレイを独立したWeb Workerで開始前に計算し、完走した相手記録を対戦へ渡す。プレイヤーの進行はCPUの選択・乱数へ入力しない。画面は相手記録の現在ターンの境界と公開済みの演出位置だけを参照する。準備中は進捗を表示し、ロビーを閉じれば計算を中止する。再読み込み後も保存済みの相手を使い、CPUを再抽選しない。

### 5.3 先行実装の記録と保存

| データ | 記録する内容 |
|---|---|
| メタデータ | 形式版、元ビルド、難易度、計算機・イベントの条件、元シード、総ターン数、結果ID |
| 初期条件 | カード・ランク・イベントの定義と、開始時のゲーム状態 |
| ターン別の境界 | 研修で確定した内容、行動開始、確定配置、カード別・イベント別の演出結果、効果解決後、会議終了後の状態 |
| 最終結果 | 得点、最終デッキ、最終状態、完走・記録完全性の検証結果 |

状態にはカード個体・所在、ステータス、トークン、研修残数、固有状態、イベント状態などを含める。記録自身や分析ログを状態内へ複製しない。計算機の入力修正などの確定前の操作は、確定した選択と結果に集約する。

中断データには専用のリプレイ記録を含め、再開時に記録位置を復元する。カード解決済みの情報やイベント予約の識別子を使い、再読み込みで同じ効果・記録が重複しないようにする。旧セーブに開始時からの記録がなければ、途中から記録を補っても完全なリプレイとして出力しない。

履歴保存では、圧縮待ちの完全データを `replayPending` として結果要約と同時に保存する。非同期で圧縮した後に `replayText` へ置き換える。圧縮完了前に再読み込みした場合は、保存した完全データから処理を再開する。圧縮・クリップボード出力の待ち時間で再プレイを妨げない。

圧縮前のデータ・圧縮後のテキストは履歴へ保存し、GASの送信ペイロードには追加しない。完全なリプレイの内部読込み処理を用意し、入出力の往復で内容・版互換性を検証する。対戦ロビーの読込みUIは0062で接続した。
