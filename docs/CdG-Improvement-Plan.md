## 1. 目指す方向と決定事項

当初の改修方針は、次のとおり。

> よりメンテナンスしやすいコードで、より不具合が少なく、繰り返し快適にプレイでき、主にスマホで滑らかな演出を楽しめて、様々なデッキで遊びたくなるカードバランス環境にして、現在の各カードのパワーを客観指標で確認しながら調整できる。

2026-10-02の相談で、ゲーム体験について以下を決定した。

- **「構築の幅」を第一にする。** 異なるカード構成・コンボ・運用方針で高得点を狙える環境を目指す。
- 毎回出たカードへの対応力と、狙ったデッキを完成させる楽しさが競合する場合は、**狙ったカードやコンボを作れることを優先する。**
- この方針を、カード性能だけでなく、研修候補の供給・取得方法・得点ルール・評価方法にも反映する。
- 計画はドキュメントとして残し、相談で決まったことを更新する。

続く相談で、以下を決定した。契約講師の詳細、具体的なカード効果・入れ替え対象、取得方法の実装方式は提案段階として区別する。

| 項目 | ユーザーが決定した方針・制約 |
|---|---|
| 難易度 | PROを土台として、新難易度MASTERを制作する |
| 構築(a) | 新たな配置先「契約講師」。配置制限の代わりにカードがターンを跨いで残り、弱めの効果や補助効果を継続して発揮する |
| 構築(b) | 多数取得・多数ドロー・多数配置で得点を稼ぐ膨張編成 |
| 構築(c) | デメリット付きカードを組み合わせ、デメリットを回避して高得点を出す |
| 構築(d) | デッキからカードを選んでドローする効果 |
| カードプール | 基本カードを含め52種類以内。新MASTERカードは旧PROカードとの入れ替えを基本とする |
| 序盤の構築 | 核となる札をゲーム序盤で決め、狙ったデッキを作りやすくする |
| 選択の上限 | カード取得は一度に3択以内、配置先は4択以内。配置後に効果の種類を宣言する選択は設けない |
| 強さの時間差 | 序盤を楽にするカードと、コンボ完成後の終盤に強烈な効果を発揮するカードの両方を収録する |
| 数値設計 | 条件やリスクに応じ、各パラメータがPROより0〜35%程度高く出ることを目安にする |
| 構築完成率 | 望んだ方針のデッキが約70%の確率で成立することを目指す |
| 下振れ | 核となるカードが全く機能しない事態を避ける手段を設けたうえで、下振れは許容する |
| 共通UI | スマホ縦画面で判断材料を一望しやすくする。配置済み効果を短縮表示し、長押しで詳細確認。長押し可能な箇所も見て分かるようにする |
| 共通演出 | 現在の演出速度を維持し、タップでスキップできる箇所を増やす |
| 共通評価 | 操作・演出とカード評価の見える化はFRESH・PRO・MASTERに共通適用する |

## 2. 調査時点のプロジェクト状況

以下は共通改修前の調査記録。実装結果と残る確認は冒頭の表と関連文書を参照する。

### ゲームとカードデータ

- HTML・CSS・JavaScriptのモジュールで構成される、8ターン制のゲーム。
- FRESH・PRO、途中保存と再開、計算機モード、イベントモード、スコア送信、難易度別ハイスコアを実装済み。
- カード定義はFRESHが49枠、PROが51枠。PROの同名カードをまとめると50種類で、基本カードには同名2枠がある。統合CSVはデータ51行。
- 調査時点で、統合CSVと難易度別CSVのカード効果は一致している。比較では改行差を正規化した。
- カード効果は日本語の説明文をパースして実行する。カード番号の重複は各CSV内で見つからなかった。

### 保守と検証

- 状態・カード・ターン・スコア・保存はモジュールに分かれている。
- `uiController.js`は約4,400行あり、画面描画・操作・演出・イベント効果の解決・計算機入力・復元などが集中している。
- カード効果、特殊トークン、操作、イベント演出、保存復元、レスポンシブ配置などのPlaywrightテストがある。
- テスト設定はDesktop Chromeのみ。狭い画面幅の検証はあるが、スマホのタッチ条件やWebKit、実機性能の検証は今後の候補。
- 現在のGitHub Actionsは静的配信が中心で、テストを実行する工程はない。
- `task.md`やREADMEには、現行実装と異なる進捗・ランク説明などが残っている。

### カード評価

- `solver/`に、自動プレイ、複数戦略の比較、カード別寄与、得点・ランク分布の集計がある。
- 人間プレイの分析資料と、多数の過去シミュレーション結果がある。4月の結果は参考資料として扱い、現在の環境の強弱を示す値としては再計測する。
- 自動プレイのカード集計は、使用回数、使用したゲームの平均点、ステータス増分などが中心。
- 人間プレイ分析で「使用率」と呼ぶ指標は、実際には最終デッキに含まれる率。実際の使用回数と区別する必要がある。
- 自動プレイには、乱数を固定した比較と、結果にカード・ルール・コードの版を結び付ける記録が不足している。

調査開始時から、既存の未コミット変更が11ファイルあり、`docs/`とスコア仕様書にも未追跡の資料があった。本計画はそれらを含む作業ツリーに基づく。並行開発のため、その内容を`dea640b`に保存した。公開中のゲームと同一の状態かは未確認。

## 6. 客観評価で確認したい指標

カードのパワーは、単独の順位に加えて、難易度・取得ターン・デッキ型・使用スタッフ・条件成立状況ごとに確認する。

| 観点 | 指標候補 | 調整時に分かること |
|---|---|---|
| 取得機会 | 候補提示率、必要札への到達率、取得ターン | 狙っても集まらないカードやコンボがあるか |
| 採用 | 提示されたときの選択率、取得枚数、削除率 | 取得機会に対して選びたいカードになっているか |
| 実際の使用 | 引かれた率、引いたときの使用率、使用回数、配置先 | 持っているだけか、構築の中で機能しているか |
| 有効性 | 効果成立率、コスト不足率、条件付き効果の成立率、実ステータス増分 | 額面の効果がどれだけ実現するか |
| 後続効果 | 情熱・発想・整理・並行・疲労による後の選択肢と得点への寄与 | 即時の数値に表れない価値があるか |
| 得点への寄与 | 同じ乱数条件でカードを差し替えた比較、平均・中央値・下振れ・目標ランク到達率 | その条件でカードを変えると結果がどう変わるか |
| 構築の幅 | デッキ型別の完成率・完成ターン・得点分布、カード構成の集中、共通の必須札への依存 | 異なる構築が成立し、高得点を狙えるか |
| MASTERの目標 | PROとの最終パラメータ差、構築成立率約70%、核の取得・ドロー・有効使用・不発理由 | 目標どおりの出力と、核が機能する構築になっているか |
| 測定の信頼性 | 試行数、ばらつき、乱数条件、コード・カード・ルールの版、評価戦略 | 結果を再現し、変更前後を比較できるか |

「最終所持率」「取得率」「実使用率」は分けて表示する。最終所持と得点の相関は観測値として扱い、カードを変更したときの得点差とは区別する。

比較する戦略も複数用意し、特定の自動プレイ戦略が選びやすいカードだけで評価が決まらないようにする。戦略の数に加え、実際に異なるカード構成・コンボになっているかを確認する。

人間プレイの記録では、通常・計算機・イベント、難易度、カード・ルールの版を区別する。取得方法が変わった前後も分けて分析する。

## 7. 狙った構築を支える仕組みの相談候補

この節はMASTER側への引き継ぎ記録であり、今後の相談・実装は別スレッドで行う。具体案は[MASTER仕様案](CdG-MASTER-Design-Draft.md)に記録する。以下は提案であり、採用は未決定。

| 案 | 狙った構築への助け | 主な設計論点 |
|---|---|---|
| 開始時の核3択と支援札3択 | 初回の取得2枚を、一枚ずつの3択で選び構築の軸を決める | 3核で複数の構築を支える対応関係、支援札の供給 |
| 序盤・中盤の適合候補 | 最大3候補の中に、核に合う支援札や完成札を含める | 対象ターン、適合の定義、プール枯渇時の処理 |
| 初回の核ドロー保証 | 最初の手札に選んだ核を含め、使う機会を確保する | 通常ドロー1枚との置換、核のコスト・条件 |
| 次ターンの選択ドロー | 付与される効果を固定し、次のドロー工程で山札の最大3候補から選ぶ | 効果分岐選択を作らず、選びたいカードへのアクセスを確保する |

契約講師・膨張・リスク回避・選択ドローは組み合わせ可能な方針として扱う。カード配置後の効果分岐や、4種類を選ぶためだけの追加の方針選択画面は提案の前提に含めない。
