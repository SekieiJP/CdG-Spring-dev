## 提案の要点

- 助言を「画面に入った時点の方針」に変更する。取得・削除の選択を仮適用して表示を変える仕組みは外す。
- 助言と光る取得候補を、同じ開始時の状態・候補・評価結果から作る。今ある選択肢で実行できることを一つ伝える。
- 「このまま次に進もう」は、削除しない選択も比較した結果として使う。「必要な札は残そう」の単純な置換にはしない。
- 背景は画面の端まで描き、見出し・×・通知などの内容は四辺の安全領域に収める。オーバーレイを閉じられない問題を先に直すことを推奨する。

## 1. 助言を固定する単位

「そのターンを迎えたときに1回」は、**研修開始時と教室会議開始時の、それぞれ1回**と解釈する案を推奨する。会議までに実際の取得・配置・効果解決が行われるため、会議ではその時点の確定済みステータスとデッキを使う。この固定単位は相談事項D1とする。

| 操作・イベント | 助言の扱い（提案） |
|---|---|
| 研修の最初の候補を提示 | 確定状態と提示候補で1回作成 |
| カードを選ぶ・選択解除・最初の2枚の片方だけを選ぶ | 文面・色・顔を変えない |
| 削除カードを選ぶ・選択解除 | 文面・色・顔を変えない |
| 顔を開閉、スクロール、詳細や設定を開閉 | 同じ助言を再表示 |
| 取得アシスト設定のオン／オフ | 強調表示だけ切り替える。助言の内容は保持 |
| 研修リフレッシュで候補を交換 | 新しい候補で1回作り直す（ユーザーが認めた例外） |
| 取得確定後、発想で新しい候補が出る | 新しい取得機会として再判定する案。D1で確認する |
| 教室会議に入る | 行動解決後の確定状態で1回作成 |
| 削除確定後、次の研修に入る | 新しい画面の開始時に作成 |
| 同じ場面を中断再開 | 同じ助言を復元。選択状態を使って再評価しない |

現在は [ahiruAdviceController.js](../game/js/ahiruAdviceController.js) が選択番号を取得し、[ahiruForecast.js](../game/js/ahiruForecast.js) が選択済みカードの追加／削除を仮適用する。初回選択・通常取得・削除の各ハンドラーから再判定も呼ばれている。写真3はこの設計に沿った動作なので、表示タイミングだけでなく評価入力も変更する必要がある。

開始時の観測と結果を一組で保持する。識別にはゲーム、難易度、ターン、フェーズ、候補セット／発想ラウンド、リフレッシュ履歴、助言ロジック版を使い、選択中のカード番号は含めない。既存の保存データにキャッシュがなければ、再開時に未選択の確定状態から一度だけ生成する。旧ロジックのキャッシュはゲームの中断データを壊さず無効化できる形にする。

補正データも開始時に使用版を確定する。起動・難易度選択時に先読みし、画面開始時に未到着なら固定式の保守的な判定を採用してその場は固定する。後から補正が届いても、現在の助言と取得順位は差し替えない。次の新しい場面で利用する。読み込み状況によって同じ画面の言葉が後から変わる経路も対象とする。

## 2. 現在値・残りターン・候補を通した取得判断

現在の [ahiruStatusPolicy.js](../game/js/ahiruStatusPolicy.js) は、推定最終値に1ずつ加えた得点の伸びから主題を選ぶ。取得を促す文面の多くは、その効果を持つ札が候補にあるかを確認していない。PROの [proAcquisitionConsistency.js](../game/js/proAcquisitionConsistency.js) に補完候補を優先する処理はあるが、候補に補完手段がない場合にも、助言側の取得命令は残る。FRESHにはこのPRO用の調整も適用されない。

提案する判定順は以下とする。

1. 現在の公式得点、入塾≦体験の制約、残り日程、保有カードの供給・コスト・配置先を確認する。
2. 次に補いたい不足を決める。将来の取得を含む統計的な補正だけで、初期状態を無条件に「順調」とは呼ばない。
3. 提示候補の中で、その不足を実際に補える選択肢を確認する。カテゴリ名だけでなく、条件・コスト・設定値・おすすめ効果・残り使用機会を見る。
4. 補えない場合は、候補内の別の有効な改善、保有カードの利用、合法で有利なリフレッシュへ分岐する。
5. 共通の評価結果から、短い助言と5秒後の強調表示を作る。両者を別々の優先順位で決めない。

保有デッキから見込む伸びと、将来の新規取得による期待上積みを分けて扱う。後者は削除・交換の価値を考える材料にするが、未取得のカードを既に持つ供給役のようには扱わない。既存の時期別の誤差補正も、そのまま「将来取得分」と読み替えず、必要なら検証データから分け直す。

通常研修の取得は必須、発想では辞退可能、初回は4枚から2枚を選ぶ、という違いを守る。「取らずに進もう」は辞退できる場面だけに使う。新しいプレイヤー操作や選択効果は追加しない。

### 写真1：初期の体験0

体験0でも、デッキの動員を先に使えば、後に教務を活かせる。そのため「体験0なら教務を取得禁止」という一律の制約にはしない。助言では**体験を先に作る前提**を明示し、取得順位の評価でもその供給が足りるか確認する。

初期は赤い危機表示より、黄色の土台づくりの案内を推奨する。例えば `まず体験。デッキの動員を活かそう`。写真1の候補には動員カテゴリがない一方、「保護者面談」は応対で体験+1を持つ。これを含む組み合わせを勧める評価になった場合は `体験を作れる応対も候補だよ` と言える。

初回2枚の光る組み合わせと、文面が指している行動を一致させる。初期の0は通常の出発点なので、現在値だけを見て一律に赤くすることも避ける。

## 3. 削除を見送る判断を追加する

現実装の「必要な札は残そう」は、主に不足・余剰の判定で特別な文面が出なかった場合の既定文であり、無削除が最善という評価結果ではない。余剰の削除候補を調べる処理も最大3候補に限られ、全ての削除と将来の新規取得を比較してはいない。

画面開始時に、削除なしと合法な削除案を同じ評価尺度で比較する。複数枚を消せる場合も、その組み合わせと役割の喪失を考慮する。評価には次を含める。

- 保有する有効札を引く確率、並行・配置先競合、条件・コストを満たせる見込み。
- 残り日程から期待する新規取得と、強い札が入った後の薄いデッキの価値。将来の実際の抽選結果は使わない。
- 不足する数値を補う最後の手段を消す損失。カテゴリだけで保護／削除を決めない。
- 最終会議など、削除しても今後のプレイ機会がない場面。

ゲーム内は事前調整した重みと固定式を用いる。将来の取得分の近似は過去の完走記録で調整し、実行中にゲームを繰り返さない。

| 評価結果 | 文面の例 |
|---|---|
| 無削除が最も高い、または明確な削除利益がなく同点時は保持 | `このまま次に進もう` |
| 不足を崩さず動員1枚の削除が明確に有利 | `動員を１枚減らしてデッキを整えよう` |
| 満足を補う応対の維持が必要 | `満足が心配。満足を伸ばす応対は残そう` |
| 削除可能枚数0、または最終会議で今後の効果なし | `このまま次に進もう` |

削除見送りと判定したことだけで緑にしない。色はSへの見通し、文面は今回の行動として分けて判断する。例えば不足が残るなら、赤／黄のまま `入塾が心配。今回は削除せず進もう` とする選択肢もある。

写真2でどの削除が実際に有利かは、画像だけから確定しない。今の「順調」を根拠に、直ちに無削除へ置き換える判断はしない。

## 4. ゲーム内のカテゴリ名で伝える

「回復札」は表示から廃止する。動員・教務・応対・庶務を使い、必要に応じて対象の数値も付ける。

| 目的 | 代表的な文面 |
|---|---|
| 体験を維持 | `体験が心配。動員を残そう` |
| 入塾を維持 | `入塾が心配。教務を残そう` |
| 満足を維持 | `満足が心配。満足を伸ばす応対は残そう` |
| 経理を維持 | `経理が心配。経理を伸ばす庶務は残そう` |

カテゴリと効果は一対一ではない。例えば「備品注文」は庶務だが満足も上げる。「スイーツ」は庶務でも経理を上げない。「保護者面談」は応対だが体験も上げる。必要な実効果を持つカテゴリを選んで文章へ入れ、必要なら `満足を補う庶務も残そう` のようにする。写真4なら、実デッキを評価して応対の維持が必要な場合に、表の満足の文面を使う。

複数カテゴリが重要な場合は、影響が大きいものへ一つの助言を絞る。カテゴリ名を並べるために25文字を超えたり、保護対象でない同カテゴリの全カードまで必須と誤解させたりしないよう、効果の修飾を使う。

## 5. 写真5：満足を補う候補がない場合の文案

写真5の候補は「日々の授業」「提出書類ファイリング」「宿題チェック」で、いずれも満足を直接増やさない。FRESHなのでリフレッシュも使えない。経理4を補う庶務や、入塾3を伸ばす教務は候補にある。

**基本案は、候補外の取得を命じる代わりに、候補内で一番有効な行動へ案内すること。** 以下から評価に合う一文だけを表示する。

| 文案 | 適用条件・使い分け |
|---|---|
| `満足を補う札は候補外。今は庶務を選ぼう` | 満足を補えないことを説明し、ファイリングが今回の最善候補であると評価した場合。写真5への第一候補 |
| `今の候補なら、庶務で経理を補おう` | 情報量を絞り、今回できる行動を優先して伝える案 |
| `応対は次の機会に。今は教務を伸ばそう` | 保有デッキの満足供給を確認でき、今回の教務取得がより有利で、残りに取得機会がある場合 |
| `満足はデッキの応対で補おう` | 現候補より保有する応対の利用を重視する案。該当する応対があり、使用機会が残る場合に限る |
| `リフレッシュで応対を狙おう` | PRO等で使用可能かつ交換の予測価値が十分高い場合。現行FRESHの写真5には使わない |
| `今回は取得を見送って進もう` | 発想で辞退でき、追加取得が不利な場合。通常研修には使わない |

「候補に応対カテゴリがない」ことだけで満足の供給なしとは判定しない。別カテゴリに満足の有効効果があれば、そのカテゴリを案内する。

### リフレッシュを勧める条件

現在の最大評価と、交換後に選べる最良候補の期待評価を比較する。後者から、残り回数を今使う機会費用・予測の不確かさを引いても、十分な利益がある場合に勧める。全候補の評価が低いという条件だけで、交換を勧めない。

現在のレアリティ、取得枚数、使用可能回数、提示・除外履歴、カード名ごとの公開抽選規則を使う。R研修の交換先へSSRを見込んだり、除外した個体と同名の全カードを除外扱いしたりしない。[cardManager.js](../game/js/cardManager.js) は残るカード名を重複なく抽選するため、単純な残存枚数比例とは区別する。

通常の「3枚から1枚」なら、同じ状態で各カードの固定式評価を一度ずつ計算し、公開された種類の抽選確率から「交換後の最大値」の期待値を計算する方式が候補になる。初回の2枚組の相乗効果やプール再構成は別扱いとし、必要ならオフラインの事前集計表を使う。公開履歴が不足する場合は、根拠の薄いリフレッシュ指示を出さない。

FRESHへリフレッシュを追加する案は、助言の修正とは別の**ゲームルール変更**。基本案は現行ルール内の改善とし、追加する場合は回数・対象・バランスを別途相談する（D3）。

## 6. 写真6：最終ターン・発想ありの場合

[日程定義](../game/js/defaultRules.js)では5月上旬は最終ターン。写真6は体験40・入塾40なので、入塾も体験の上限に達している。候補3枚に体験を上げる効果はなく、将来の通常研修で動員を取るような案内はできない。

一方、既に所持している発想1個は、この研修中の追加取得に使える。今回取得する「教材研究」が行動時に生む発想は、次の研修がないため別扱いとする。

| 文案 | 適用条件 |
|---|---|
| `体験は候補外。発想の追加候補も見よう` | 写真6のように、今使える発想が残っている |
| `体験は候補外。デッキの動員を活かそう` | 保有デッキに、このターンに使える動員がある |
| `体験を作ってから教務を活かそう` | 保有カードで体験を先に作り、候補の教務を使う方針が成立する |
| `今の得点を守って進もう` | 上積みが難しく、既に得た得点を不要なコストや配置で失わないことが有効 |

既存の得点を守るために配置を控えることと、通常研修の取得を辞退することは区別する。光る候補には、残りのデッキ・コスト・入塾上限を踏まえた、今の候補内の順位を使う。

## 7. Edge-to-Edgeと情報画面・通知

### 0057に残る具体的な原因

[style.css](../game/css/style.css) には以下の組み合わせがある。

- 通常本文は `--app-safe-top` の上端余白を持つ。
- 上端を覆う `body::before` は固定配置で `z-index: 11000`。
- 情報オーバーレイは固定配置・上端0・`z-index: 1500`。そのヘッダーも上端0で、安全領域の余白がない。
- フロート通知は上端16px相当・`z-index: 3000`。上端の安全領域を考慮していない。

安全領域が正の端末では、ヘッダーや通知が上端へ入り、さらに共通の覆いの背後になる構造である。本文のpaddingは、独立した固定オーバーレイや通知を保護しない。写真7・8と整合する有力な原因であり、端末ごとの実際のinset・表示モードは今後の実機確認で採取する。

### 推奨する構造

背景を四辺の端まで描き、重要な内容を安全領域へ内側に配置する。[WebKitの説明](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)も、全面表示の指定と、重要な内容への安全領域の余白を組み合わせる形で説明している。

| 対象 | 修正方針 |
|---|---|
| 安全領域の共通値 | 上下左右の `env(safe-area-inset-*, 0px)` を共通化。既存の `--app-safe-top` を含め整理し、端末名や59px固定で判定しない |
| 背景・暗幕 | 画面端まで描く。通常画面の上端を覆う層を、ダイアログの内容より手前へ置かない |
| 情報画面のヘッダー | ヘッダー自身の背景は上端まで延ばし、タイトル・×の領域を上／左右の安全領域＋通常余白の内側へ置く |
| 本文 | ヘッダーを残し、本文部分だけをスクロールさせる。最下段も下端の安全領域へ隠れないようにする |
| × | 44px以上のタップ領域。回転・スクロール後も、安全領域内で見えて押せる状態を維持 |
| 復元などの通知 | 安全領域と、表示中の通常／情報画面ヘッダーの下を基準に配置。×を覆わず、情報通知はタップを妨げない。左右も安全領域内で折り返す |
| 高さ | 動的な表示領域に合わせる `100dvh` と従来値のフォールバックを検討。上下insetも引いた内容領域を確保し、二重に余白を足さない |
| 適用範囲 | デッキ内訳、スケジュール、設定、結果履歴、共通の情報表示、復元を含むフロート通知をまとめて対象にする。他のモーダルも共通の安全領域規則へ合わせる |

動的なブラウザUIに応じた高さと、Dynamic Islandを避ける余白は別の役割。[WebKitの動的viewport単位の説明](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/)を参照し、`dvh`だけで上端の問題が解決したとは扱わない。可視領域の変化にCSSだけで対応しきれない箇所は、既存の [mobileLayoutController.js](../game/js/mobileLayoutController.js) の計測と役割を整理する。

### PWAのステータスバー設定

0057は `black` に変更済み。Appleの仕様では、`black` は内容をステータスバーより下に、`black-translucent` は画面全体に表示する設定である。[Appleの仕様](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariHTMLRef/Articles/MetaTags.html)。

今回のEdge-to-Edge方針では、**内容側のinsetと重なり順を修正したうえで、PWAは全面表示の `black-translucent` を採用する案を推奨**する。設定だけ先に戻すことはしない。Safari通常タブとホーム画面起動を分け、実際の表示領域に応じた余白が一度だけ適用されることを確認する。上端を不透明な帯で隠すだけの対応にはしない。
