# 同僚と対戦の設計

2026-11-13の実装仕様。調査対象は`v20261110-0065`。実装のビルド番号は`v20261110-0066`。

同じ部屋コードでそれぞれの教室を運営し、完走後に結果を見せ合う。コードの発行、入力、シードの決定、再挑戦の判定はブラウザ内で完結する。プレイヤー間で共有するのは部屋コードと各自の結果画面。

## 部屋を作成して始める

対戦ロビーに「同僚と対戦」を追加する。「部屋を作成」と「部屋に入る」を同じ画面から選べる。

1. 代表者はFRESHかPROを選んで「部屋を作成」を押す。初期選択はタイトル画面の難易度に合わせる。
2. 作成と代表者のプレイ開始を一続きの操作にする。初回研修の中断保存を確定したらコードを表示し、「コードをコピー」と「OK」を置く。OKで初回研修に進む。プレイ中も設定からコードを表示してコピーできる。
3. 他のプレイヤーは「部屋に入る」でコードを入力する。形式が正しければコードに対応する難易度を表示し、その難易度で開始する。代表者の端末が起動しているか、すでに完走したかに関わらず、形式が正しいコードを受け付ける。

作成と開始を一続きにすることで、未開始の部屋を管理する保存枠が要らない。開始中の連打を止め、データ読み込み中にロビーを閉じた場合は開始を取り消す。

### コードとシード

- コードは`00000000`から`99999999`までの数字8桁の文字列。先頭の0を表示・コピー・保存に残す。
- 末尾が偶数ならFRESH、奇数ならPRO。入力側の難易度をコードで固定することで、コードだけを伝えても同じ条件で遊べる。
- 作成時は0以上50,000,000未満の整数`n`をランダムに選び、FRESHなら`2 * n`、PROなら`2 * n + 1`を8桁にゼロ埋めする。たとえば`01563828`はFRESH、`01563829`はPRO。
- 入力は数字キーボードを出すテキスト欄を使う。前後の空白を除き、全角数字を半角に直してから、8桁の数字に完全一致するかを検査する。9桁の貼り付けを8桁へ切り詰めず、不正な入力には「部屋コードは数字8桁で入力してください」と表示する。
- シードは正規化済みコードに`room:`を付けた文字列。例は`room:01563829`。コードの発行とプレイ中の抽選には別々の乱数を使う。コードの照会・衝突確認・有効期限の処理は設けない。

## 中断・リタイア・再挑戦

中断データは従来の全モード共通の1件を使う。進行中はそのプレイを再開し、完走して結果が確定するか、確認のうえリタイアして中断を削除すると、新しい部屋を作成できる。設定のやり直し操作を部屋プレイ中は「リタイア」として案内する。タブを閉じたり再読み込みしたりしたときは、中断地点から再開する。

再挑戦の判定単位は、同じブラウザプロファイル、同じ配信元に保存された部屋コード。配信元はプロトコル・ホスト・ポートで決まる。別のブラウザを使った場合は別の記録になり、サイトデータを消去すると記録も消える。各コードの開始済み印を専用の端末内キーに保持し、プレイ履歴50件の入れ替えや中断の削除では消さない。

- 作成・入室のどちらでも、同じコードで過去に開始済みなら、開始前に「この部屋コードで遊んだことがあります。成績には&lt;リベンジ&gt;マークがつきます。」と表示する。OKで進み、閉じた場合はロビーに戻る。
- 初回研修の候補と中断を保存し、開始済み印を書き込んでからプレイを始める。入力だけ、通知を閉じた場合、カードデータの読み込みに失敗した場合は開始済みにしない。完走前のリタイアも、開始を確定した後なら次回の再挑戦判定に含める。
- `revenge`は開始確定時に決め、中断と結果に保存する。再開では開始済み印を照会して再判定せず、保存した印を使う。互換ビルドが変わっても、端末内で同じコードを開始した記録は引き継ぐ。

初回保存と開始済み印の書き込みは、操作を受け付ける前に完了させる。開始直前に中断の有無と開始済み印を読み直す。書き込みに失敗した場合は、当該試行の初回保存だけを取り消し、ロビーに原因を表示して再試行できるようにする。2つの書き込みの間で再読み込みされた場合は、残った中断から開始済み印を補い、保存時の`revenge`で再開する。

## プレイ条件

コードから得たシードと難易度を既存の1人用初期化へ渡す。通常の研修、手札、配置、効果演出、教室会議を使い、取得アシストとあひる先生の助言はプレイヤーの設定に従う。イベントと計算機モードはこのプレイ中だけ適用外にし、日付や端末の設定による条件差を避ける。

相手の状態を持たないため、プレイ画面には自分のステータスとデッキを表示する。成績の比較は完走後に行う。同じ部屋コード、互換性のあるビルド、同じ操作なら同じ結果になる。取得・リフレッシュ・発想研修などの操作が異なれば、同じコードでもその後の抽選や手札が分かれる。

## 結果発表

部屋プレイ専用の一画面で、部屋コード、難易度、ルールの版、リベンジ印、合計点、ランク、評価表、最終デッキを表示する。合計点は通常どおり`displayScore`。リベンジ印は表示に使い、得点計算には渡さない。

縦向きの配置例。

```text
部屋 01563829    PRO
ルール20261110    リベンジ
           10点   A+

項目         値     評価点
入退差       25       +4点
退塾 ↓        0       +1点
体験         36       +3点
満足         39       +2点
経理         24         —
入塾         25         —

最終デッキ
［画像］［同じ画像］［画像］…

［対戦ロビー］   ［メニュー］
```

同点時は既存の対戦判定と同じく、入退差が多い、退塾が少ない、体験が多い、満足が高い、経理が高い、の順で先に差がついた項目を見る。入塾は4ステータスの一つとして表の末尾に置く。こうすると体験・入塾・満足・経理の値と、基準別の成績を一つの表で確認できる。

体験の評価点には動員目標の得点を使い、満足の評価点はPROで表示する。評価点がある項目は0点や減点も値で示し、配点のない項目は「—」。FRESHの精度加点がある場合は、基礎点との差を表の下に1行で表示する。

各行の左端にカラーバーを置く。入退差は金のグラデーション、退塾は赤から黒へのグラデーションとする。体験・入塾・満足・経理にはゲーム中のステータス表示と同じ単色を使う。 行全体の背景にも各項目の色を12%の濃さで敷く。入退差の背景には金、退塾の背景には赤を使う。

最終デッキはレアリティ順のサムネイル一覧とする。同じカードが複数枚あれば、カード1枚につき画像を1つ表示する。カード名を読み上げに使い、画像が欠けた場合も代替表示を残す。カード画像の設定に関わらずこの一覧を表示し、カード名の本文と効果説明は履歴から確認できるようにする。

対戦ロビーに戻ると「同僚と対戦」を開く。タイトルへ戻る、プレイ履歴、お気に入り、リプレイのコピーと視聴、結果の画像保存、送信状態はメニューに収める。結果を見せ合う画面には進行中のヘッダー・ログ・前回成績を重ねない。

### 一画面に収める寸法

- 表示域はブラウザの操作バーとセーフエリアを考慮する。縦向きでは部屋情報と得点、評価表、デッキ、操作の順に積む。高さが短い横向きでは評価表と部屋情報・得点・デッキを横に並べる。
- 結果専用の文字サイズを使う。アプリの文字サイズ設定を切り替えても、コンパクト表示で合計点46px、表の値と評価点22px、項目名18pxを目安にする。余裕がある画面では拡大する。数値は桁をそろえ、操作ボタンは高さ44px以上。
- 検収下限はセーフエリアを引いた表示域で縦320×440px、横568×256pxとする。実際に表示するサムネイル約20枚を基準に、コンパクト時は10列を目安に2段で配置する。画像は縦向きで28px、短い横向きで22pxを目安にする。表示数が20枚を超える場合は、画像寸法と列数を調整して全枚数を表示する。
- 検収下限より小さい表示域にも全項目を残し、余白、画像、列配置を先に調整してから、必要に応じて文字を縮めて一画面に収める。上記の文字サイズを保てることは、検収下限以上で確認する。

実装した画面に同じカードを含むサムネイルを20枚と24枚並べ、精度加点を含めて、縦320×440pxと390×640px、横568×256pxで切れや重なりがないことをChromiumで確認した。文字と画像を表示域に合わせることで、縦320×380pxと横568×220pxにも収まった。

### 結果画像を保存する

1人用、イベント、計算機、対戦を含む全モードの結果画面に「結果を画像で保存」を置く。同僚対戦では結果のメニューから使う。PNGには行のカラーバーと淡い背景色を含む評価表、合計点・ランク、カード1枚ごとのサムネイルを載せる。部屋プレイではコードとリベンジ印、相手がいる対戦では勝敗と両者の成績・最終デッキを載せる。

画像の末尾に、完走時に記録したプレイ終了日時と利用者UUIDを小さく表示する。日時には保存時の端末のタイムゾーンを添える。操作ボタンを除いた画像をブラウザで作成し、その端末へダウンロードする。

## 結果の保存と互換性

| 対象 | 扱い |
|---|---|
| 中断 | `gameState.room`に`{ code, revenge }`を追加し、難易度、シード、乱数状態と一緒に既存の中断データへ保存する。従来データでフィールドが無ければ通常どおり復元する |
| 端末内履歴 | 既存の履歴に自分の結果を保存し、「同僚と対戦」、コード、リベンジ印を表示する。お気に入りとリプレイを既存の履歴から扱う |
| 自己ベスト | コードを指定して同じシードに挑戦できるため、初回とリベンジのどちらも対象外とする |
| GAS | これまでの対戦と同様に、本人の完走結果を既存の送信・再送キューで受け付ける。通常のルールで計算した結果として送信し、部屋コードと再挑戦の情報は端末側の記録で扱う |
| リプレイ | 完走し記録がそろった場合に、既存の`CDGR1.`で自分のシードと操作列を書き出す。部屋の状態や開始済み印に依存せず復元する |

部屋コードはビルドを指定しない。結果に表示するルールの版は、記録したビルド番号の上8桁とする。コード・難易度・ルールの版を見比べて、同じ条件での結果かを確認できる。将来カードや抽選が変わっても8桁のコードは入力でき、その時点のビルドで挑戦する。

部屋の情報は既存の保存形式へ任意項目として追加する。既存のカード・抽選・得点・操作列を使うため、この機能の追加自体はリプレイの互換番号を変える理由にならない。部屋プレイを保存して対応前の版へ戻した場合、旧版は部屋情報を読み取れないため、部屋としての再開には対応版を使う。

## 実装順と確認項目

1. コードの生成・検証・難易度・シードを一か所で定義する。`battleController.js`のロビーから`uiController.js`の開始処理へ渡し、`GameState.battle`には相手のいる2方式を保持する。部屋は`GameState.room`で扱う。
2. 初回研修の保存結果を開始処理に返せるようにして、`saveManager.js`の中断復元、リタイア、開始済み印をつなぐ。完走後は既存の結果確定と中断削除を使う。
3. `scoreManager.js`の自己ベスト判定、`resultController.js`の履歴、結果画面の表示をつなぐ。評価順は`battleReplay.js`の比較順を参照し、得点には既存の計算結果を使う。
4. 下表の確認を行い、既存の1人用・リプレイ対戦・CPU対戦・中断復元・履歴とGAS送信の回帰テストを通す。

| 確認 | 検収条件 |
|---|---|
| コード | 両難易度の作成、先頭0、未発行のコード、全角・前後空白、7桁・9桁・記号入りを確認する |
| シード | 別々のブラウザコンテキストで、代表者と参加者が同じコード・操作で初回候補、後続の研修、手札、最終結果まで一致する |
| 開始と再開 | 開始前の取消・失敗は次回のリベンジにならず、完走・リタイア後に同じコードで始めると警告と印が付く。途中の再読み込みでは印を再判定せず同じ進行を復元する。結果履歴の入れ替え後も開始済み印が残る |
| 作成の制限 | 進行中は次の部屋を作れず、完走またはリタイアで作れる。開始ボタンの連打で二重登録せず、送信待ちでも次のプレイへ移れる |
| 結果画面 | FRESHの精度加点、PROの満足点、退塾の減点、同じカードのサムネイル、リベンジを表示する。縦横の最小寸法、iPhoneとAndroidの通常寸法、デスクトップで、各文字サイズ設定のまま全結果の境界が表示域内に入り、縦横ともスクロールを要しない |
| 結果画像 | 結果画面からPNGをダウンロードできる。保存画像に成績、全カードのサムネイル、プレイ終了日時、利用者UUIDが表示される。対戦結果は相手と勝敗も含む |
| 保存・送信 | 通常の自己ベストを更新せず、本人の結果だけを既存キューへ渡す。部屋プレイのリプレイを既存のリプレイ対戦・防犯カメラで読める。旧データを読み込むと従来のモードで再開する |

同点処理と対戦結果の保存方針は[既存対戦の設計書](CdG-Async-Battle-Design.md)を参照。
