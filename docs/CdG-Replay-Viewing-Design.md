# 教室防犯カメラ・お手本プレイ：要件と実装計画

対象ビルド：`v20261110-0065`

公開先：`CdG-Spring-dev`の`game/`。本番リポジトリへの公開は今回の依頼範囲に含めない。

## 研修候補の順序

同じ難易度・カードデータ・シードから、同じレアリティ別の研修デッキを生成する。初期化時と、そのレアリティの全個体を提示し終えた後だけシャッフルする。候補の提示時には再抽選せず、デッキの先頭から取り出す。

同じ提示内で同名カードが重なるときは、その個体をデッキ内に残し、次の異なる名前を取り出す。残りに未提示の個体がある間は、候補枚数を埋めるためだけに再シャッフルしない。

同じ候補提示履歴なら、取得したカードを変えても次回の候補順は変わらない。通常研修と発想研修は同じSRデッキを共有するため、追加の候補提示やリフレッシュを行った分だけ順序が先へ進む。リフレッシュは次回の同レアリティ候補を先に取り出し、現在の候補は現行ルールどおり以後の循環から除く。

## CPUとの同一シード対戦

- CPU対戦ロビーにチェックボックスを置く。初期値はオン。
- 対戦のたびにCPU用の新しいシードを作り、オンならプレイヤーもそのシードを使う。
- CPUとの同一シードはハイスコア記録・スコア送信の対象とする。
- リプレイとの同一シードだけ、従来どおりハイスコアの対象外とする。履歴・スコア送信は受け付ける。
- 再戦でも新しいCPUプレイとシードを生成する。チェック状態は再戦設定へ引き継ぐ。

## 教室防犯カメラ

- リプレイを読み込み、ターンごとの取得・配置・削除の場面を閲覧する。
- カードの取得・移動・削除は操作できない。⏪ / ⏩で場面を戻したり進めたりする。
- UIは「いつもの画面」を採用する。「取得／配置／削除」の切り替えボタンは置かず、記録順にページをめくる。現在のページ番号を表示する。
- 配置場面では、実際に配置したカードと、効果解決後のステータスを表示する。
- 各場面の実際の状態・候補・所有札を使い、既存CPU方略が同じ場面で選ぶカードへ🐤を表示する。別の通しプレイの選択を流用しない。
- 配置ではCPUが使うカードへ🐤を付ける。CPUアイコンから選択理由を確認できる。
- スマートフォン向けに3つのUI案を示し、配置と時間移動の方式を比較できるようにする。

## お手本プレイ

- 入力リプレイと同じ難易度・シードでCPUをプレイさせ、CPU自身のリプレイを出力する。
- 元リプレイのイベントを引き継ぐ。計算機の入力UIは引き継がず、CPUの選択で進める。
- 生成後はワンボタンで防犯カメラへ移動し、取得・配置・削除を確認できる。
- 通常の対戦CPUと同じ固定方略を使う。別の軽量アシストへ置き換えない。

## 保存・互換性

上8桁が変わるため、0064以前の中断データ・リプレイとの互換性は維持しない。形式名は`CDGR1.`を維持する。

ユーザーの追加指示により、コードはシードと確定した操作列を中心とする。取得候補・ステータス・所有札の各時点の状態や、カード・評価表の一覧はコードへ含めない。互換ビルドのカード・ルールで操作を再実行し、その場で視聴用の状態を復元する。上8桁が異なるビルドはゲームの復元前に拒否する。

操作列には取得した候補の番号、計算機入力のカード番号、リフレッシュ回数、配置・削除したカードの個体番号、必要な手札・山札の順序を持たせる。配置を取り消して手札へ戻すなどの操作によって変わる順序も、確定時点の整列操作として再現する。結果の照合には小さなチェックサムを使い、結果のステータス一覧は保存しない。

プレイ中の中断・診断用の記録と、リプレイコードの形式は分ける。CPU判断に必要な候補・判断前の状態は、読み込み時の再実行中にメモリ上へ作る。

ゲーム中の中断保存と独立した閲覧状態を使い、視聴やCPU生成で進行中のゲームを上書きしない。閲覧・お手本生成はプレイヤーのハイスコア記録や実スコア送信を発生させない。

## 検証と現在の進捗

固定順・重複・一巡境界・リフレッシュ・発想研修の共有、CPU同一シードのハイスコアと送信を重点的に確認する。CPU方略そのものは保持し、抽選規則の変更で変わる基準プレイを区別する。

固定順の抽選とCPU同一シードの設定・ハイスコア判定を実装した。`node scripts/set-build-version.mjs v20261110-0065`で版と参照をそろえた。

単体全302件が成功。CPU同一シードの初期候補一致、オフ設定、完走と送信、再戦での新しいシードを、関連ブラウザ9件で確認した。ローカルのデスクトップ・iPhone 12寸法・Android寸法はすべてChromium。公開前CIはデスクトップChromium・iPhone寸法のWebKit・Android寸法のChromiumで全件を実行する。

固定PRO方略の基準3プレイは、新しい研修順で13・11・14点となった。方略モジュール・モデルのハッシュは変更せず、変更した抽選規則に合わせて基準の取得・配置解決・削除と最終結果を記録し直した。旧基準はGit履歴に残る。3件の結果から平均的な強さの向上を判断しない。

### 視聴UIの3案

| 案 | 構成 | 比較する点 |
|---|---|---|
| いつもの画面 | 既存のカード画面に近い構成。ステータスと記録の配置・候補を表示し、ページを前後に移動する | 普段のプレイとの対応が分かりやすい |
| 記録をたどる | 左にターン・取得・配置・削除の記録、右に選んだ場面の内容 | 記録の順序を追いやすい。狭い画面ではカード領域が小さくなる |
| 並べて比較 | 記録の選択と、同じ場面でのCPUの選択を2列で表示 | 選択の違いを見比べやすい。同じカードを両列へ表示する場合がある |

操作できる表示例を3案作成し、ユーザー回答により「いつもの画面」に決定した。「取得／配置／削除」の切り替えボタンを置かず、⏪ / ⏩で記録順にページをめくる。カード自体は操作しない。

シードと操作列によるコード出力・復元、場面ごとの固定CPU判定、イベントを引き継ぐお手本生成を実装した。通常プレイの結果画面・履歴と、タイトルのコード入力から視聴へ進める。お手本はコピーでき、ワンボタンで視聴へ移れる。

取得のCPU判断には、復元した時点の候補・所有札・ステータス・公開された提示と除外の履歴を渡す。元プレイヤーの選択・配置後の値・将来ターン・最終結果は渡さない。イベントと計算機でも固定モデルの重みを使い、イベントの実効果はゲーム状態で解決する。計算機の発想一括入力は、固定CPUの通常の発想研修と同じ1枚ずつの判断を繰り返す。

通常プレイでは重い視聴用の判断前状態を保存せず、コードの読み込み時に再構築する。FRESHの測定例ではコード630文字、圧縮前の操作列837バイト。長さは選択・配置・削除の内容によって変わる。

配置取消で変わる手札・山札の順序、互換性のないビルドを復元前に拒否する動作、FRESHの全場面とPROの途中場面で固定CPU自身の選択を再現する動作を単体検証した。通常・計算機・イベント・併用をFRESH/PROそれぞれで完走したブラウザ8条件では、復元したステータス・デッキ・カード解決の結果が元プレイと一致した。

実ブラウザでは、視聴の前後移動、配置の解決後ステータス、🐤からの理由表示、進行中のプレイと保存データの保護を確認した。FRESHのイベント・計算機の記録とPROの記録からお手本を作り、同一シード・難易度・イベントの引き継ぎ、計算機を引き継がないこと、コピーと直接視聴、追加のスコア送信がないことも確認した。

採用後のUIでは、⏪ / ⏩で1ページずつ移動し、中央に現在ページと総ページ数を表示する。ページをめくると内容の先頭へ戻る。取得・配置・削除の専用切り替えボタンやジャンプ用の選択欄は置かない。このUIで3端末寸法の視聴・お手本生成12件が成功した。

公開前CIと開発サイトへの配信後の確認結果は[公開PR](https://github.com/SekieiJP/CdG-Spring-dev/pull/10)へ記録する。配信後はビルド番号・必要なモジュールの読み込み・同一シード設定・視聴・お手本への直接移動を確認し、ゲーム状態や保存データの変更と余分な実スコア送信がないことを確認する。
